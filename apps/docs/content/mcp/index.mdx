```bash
claude mcp add husk -- npx -y @husk-ai/mcp
```

That is the whole install. There is no second step, no account, and no config file to
edit by hand.

Restart Claude Code and the model has a Linux machine: a shell, a filesystem that
persists across tool calls, and a way to publish a port.

## Verify it

```bash
npx -y @husk-ai/mcp --help      # options, printed to stderr
```

The protocol itself is easy to check by hand — the server speaks JSON-RPC over stdio, so
two lines of input list its tools:

<Terminal>
{`$ printf '%s\\n%s\\n' \\
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"probe","version":"0"}}}' \\
  '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' \\
  | npx -y @husk-ai/mcp 2>/dev/null | jq -r 'select(.id==2) | .result.tools[].name' | head -9
workspace_create
workspace_list
workspace_open
workspace_read
workspace_write
source_add
workspace_export
workspace_open_ui
shell`}
</Terminal>

The rest of the list is the computer's: the file tools, `expose_port`, `browse`,
`computer_info`, fifteen `browser_*` tools, `hand_off`, `hand_off_done` and
`computer_open_ui`. An app that gives up on a long call, as this probe would, also gets
`job_wait`, and an app that renders MCP Apps gets the computer card's two tools.
`--profile starter` lists the workspace tools alone.

## Transports

Stdio, for the chat apps on this machine. Chat apps on the web (claude.ai, ChatGPT)
reach Husk over streamable HTTP instead, through `husk serve --remote`: see
[Chat apps on the web](/guides/remote-access). A remote chat gets the computer tools
alone, since the workspace tools work on this machine's files.

## Nothing is created until it is used

Adding the server has to cost nothing, or people uninstall it. So:

- No machine at startup.
- No machine on `tools/list`.
- The first tool call creates one, and only one even under concurrent calls.

The machine is named `mcp-<session key>` and kept: it has no idle or lifetime limit of
its own. After ten minutes with no Husk call it is stopped, and the chat's next call
starts it again. When the client disconnects (SIGINT, SIGTERM, or stdin closing) it is
stopped, not destroyed; `--keep` leaves it running. Only you delete it: `husk rm`
removes it, keeping its files and browser logins for its next computer on Docker and
Podman, and the console's Delete or `husk rm --erase` takes those too.

## What the model is told

The first tool result of a session is prefixed with one honest line about the machine.
A model that believes it is contained when it is not will take risks it otherwise would
not, so this is not optional and not buried.

On a container provider:

```text
[husk] docker container cmp_8v9z, isolated from the host. /work persists for this session.
```

On the `local` provider:

```text
[husk] local computer cmp_8v9z on real Linux via Ubuntu. This is a guarded working
directory, NOT a sandbox: file tools are confined to /work and destructive commands are
refused, but shell commands can still reach anything your user can on the host --
filesystem, kernel and network. Keep secrets and untrusted input out of it. Start Docker
for real isolation.
```

On anything else:

```text
[husk] computer cmp_8v9z on ssh. /work persists for this session.
```

The server also sends MCP `instructions` at initialisation: a paragraph on the workspace
tools, then one on the computer's, which begins:

> Husk gives you a computer, usually a Linux container; /work persists for this session.
> Call `computer_info` once before assuming a runtime or even a POSIX shell: on Windows
> without WSL it is cmd.exe.

It goes on to say when to use `browse`, `browser_*` or `shell`, to take a
`browser_snapshot` before clicking, to retry an error once and then explain, and to
`hand_off` a login, 2FA, CAPTCHA or payment prompt rather than type the user's
credentials. Under `--profile starter` the second paragraph says the computer tools are
off until the user enables them; a remote chat gets the computer paragraph alone.

## Options

```text
--profile <name>    starter (saved workspaces) | computer (all tools; default)
--session <key>     reuse a named machine (default: unique to this server process)
--provider <name>   docker | podman | local | ssh | fly  (default: best available)
--flavor <name>     base | python | node | full          (default: full, which runs the browser)
--network <mode>    none | egress | full                 (default: full, minus internal addresses)
--network-strict    refuse a provider that cannot enforce --network for every process
--memory <mb>       memory ceiling
--cpus <n>          cpu ceiling
--keep              leave the machine running after the client disconnects
--daemon            run the shared Husk that every chat's tools go through
                    (started for you on the first tool call; HUSK_DAEMON=off
                    keeps tools in each chat's own process)
--jobs              run the job host: bots' schedules, webhooks and chat
                    triggers (the shared Husk starts it when a bot has one)
-h, --help
```

`--network-strict` needs `--network`, and refuses to start without it. The shared Husk
logs to `~/.husk/daemon.log` and the job host to `~/.husk/jobs.log`; the shared Husk
listens on `HUSK_PORT`, 7377 by default.

`--session` also reads `$HUSK_SESSION`. Two sessions, two machines, two filesystems, one
client:

```bash
claude mcp add husk-api -- npx -y @husk-ai/mcp --session api --flavor python
claude mcp add husk-web -- npx -y @husk-ai/mcp --session web --flavor node
```

<Note>
`--provider`, `--flavor` and `--network` are passed through without validation. A typo
such as `--flavor pyhton` is not rejected by the MCP binary; it reaches the runtime,
where it falls back to the `base` image plan. The CLI's own `husk up --flavor` does
validate, and rejects it with a usage error.
</Note>

## stdout is the protocol

stdout carries JSON-RPC and nothing else. Every log line goes to stderr. A stray
`console.log` corrupts the stream and the client dies silently, which is why
`HuskMcpServer` takes its logger by injection and defaults it to a stderr logger.

If you are debugging, read stderr:

```bash
npx -y @husk-ai/mcp 2>/tmp/husk-mcp.log
```

## Which provider you get

Whatever `auto` picks, unless you name one. Run `husk doctor` to see which that is before
you wonder why the model is reporting a Windows path.

If Docker is running, you get a container and the isolation note says so. If it is not,
you get the `local` provider and the note says that instead — which is the point of the
note.

## Other clients

Any MCP client that can launch a stdio server works the same way, and `husk setup`
writes each app's entry for you. Cursor takes a JSON block rather than a CLI command:

```json title="~/.cursor/mcp.json"
{
  "mcpServers": {
    "husk": {
      "command": "npx",
      "args": ["-y", "@husk-ai/mcp", "--session", "cursor", "--flavor", "python"]
    }
  }
}
```

Zed names the key `context_servers`, in its `settings.json`, and VS Code `servers`.
[docs/clients.md](https://github.com/Hotragn/husk/blob/main/docs/clients.md) has each
app's file and what it supports.

The tools listed above are the whole surface, whatever the client, apart from
`job_wait` and the card's two. Their behaviour, their `dangerous` flags and their
arguments are the same ones the agent loop uses — see
[tools in a husk.yaml](/reference/husk-yaml#tools) and
[Approvals](/security/approvals#which-tools-are-dangerous).
