`husk serve` exposes a JSON control plane on `127.0.0.1:7377`. Everything below was
read out of `packages/server/src/routes/`, where the code wins. The routes clients use
most have their shapes here; [Other routes](#other-routes) lists the rest, and
[`docs/API.md`](https://github.com/Hotragn/husk/blob/main/docs/API.md), the contract the
server is tested against, has every shape.

```bash
husk serve
curl -s localhost:7377/health
```

```json
{ "ok": true, "version": "0.2.0", "protocol": 1, "uptimeSec": 8 }
```

## Conventions

- Base path `/v1`. JSON in, JSON out, unless noted.
- `/health` is at the **root**, not under `/v1`, and never needs a token. Neither do the
  console's page and assets (a `GET` outside `/v1`) nor `/v1/a/*`, where a chat app such
  as Slack posts its events, checked against that app's own signature.
- IDs are opaque strings. Never parse them.
- Timestamps are ISO 8601 UTC.
- Every response carries `X-Husk-Version`.
- Request bodies cap at 32 MB. `X-Forwarded-For` is **not** trusted.
- CORS is off by default. `ServerConfig.corsOrigins` turns it on.

### Auth

When `HUSK_TOKEN` is set, every request to a `/v1` route but `/v1/a/*` needs
`Authorization: Bearer <token>`. Comparison is constant-time.

When it is not set, no token is asked for — but the server only ever reaches that state
on a loopback bind, because it refuses to start otherwise:

```text
error refusing to bind 0.0.0.0 without an auth token: this API can execute shell commands
hint:  set HUSK_TOKEN=$(openssl rand -hex 32) before `husk serve --host 0.0.0.0`, or bind 127.0.0.1
```

Token or not, a web page cannot drive the server:

- A request whose `Origin` is not `localhost`, `127.x` or `[::1]` is refused with 403,
  WebSockets included.
- On a loopback bind, a request whose `Host` is not one of those names is refused, with
  401 without a token and 403 with one, so DNS rebinding reaches nothing.

Browsers cannot set headers on `EventSource` or `WebSocket`, so for those two
transports only — detected by `Accept: text/event-stream` or an `Upgrade: websocket`
header — a `?token=` or `?access_token=` query parameter is accepted.

### Errors

```json
{ "error": { "code": "E_COMPUTER_NOT_FOUND",
             "message": "no computer with id cmp_x",
             "hint": "run `husk ps` to list computers" } }
```

Status is derived from the code: an explicit table first, then two suffix rules.

| Code | Status |
| --- | --- |
| `E_NO_CREDENTIALS` | 401 |
| `E_SPEC_INVALID` | 422 |
| `E_QUOTA`, `E_BUDGET_EXCEEDED` | 429 |
| `E_NOT_IMPLEMENTED` | 501 |
| `E_PROVIDER_UNAVAILABLE`, `E_MODEL_UNAVAILABLE` | 503 |
| `E_EXEC_TIMEOUT` | 504 |
| `E_COMPUTER_HELD`, `E_COMPUTER_IN_CHAT` | 409 |
| anything ending `_NOT_FOUND` | 404 |
| anything ending `_DENIED` | 403 |
| everything else | 500 |

A body the server cannot read keeps the status the parser gave it: JSON that does not
parse is a 400 with `E_SPEC_INVALID`, and a body over its route's cap a 413 with
`E_QUOTA`, whose hint names the cap.

The server declares nine codes that `@husk-ai/core` does not: `E_HUSK_NOT_FOUND`,
`E_RUN_NOT_FOUND`, `E_APPROVAL_NOT_FOUND`, `E_HANDOFF_NOT_FOUND`, `E_BROWSER_NOT_FOUND`,
`E_TRANSCRIPT_NOT_FOUND` and `E_ROUTE_NOT_FOUND` land on 404 through the suffix rule;
`E_COMPUTER_HELD` and `E_COMPUTER_IN_CHAT` are 409. [Error codes](/reference/errors) is
the full list.

### Streaming

Streaming endpoints are Server-Sent Events: `Content-Type: text/event-stream`, one
`data:` line per event carrying a JSON object, a `: ping` comment every 15 seconds, and
a terminating `event: done`. A failure mid-stream is an `event: error` frame carrying the
usual error body, then `event: done`.

A client that stops draining the socket for 60 seconds is treated as gone: the stream
closes and the run it was driving is aborted. A closed browser tab stops spending
tokens.

### Idempotency

`POST`, `PUT`, `PATCH` and `DELETE` honour an `Idempotency-Key` header. A replay returns
the recorded status and body with `Idempotency-Replayed: true`.

The cache is in memory, keyed on `<METHOD> <url> <key>`, with a 15-minute TTL and a
1000-entry soft cap. It does not survive a restart, and it does not cover streaming
responses — a retried streaming request runs the agent again.

## Health and capability

GET /health     -> 200 { ok, version, protocol, uptimeSec }

## Computers

```text
GET    /v1/computers            -> { computers: ComputerInfo[] }
POST   /v1/computers            body: ComputerSpec -> 201 ComputerInfo
GET    /v1/computers/:id        -> ComputerInfo
DELETE /v1/computers/:id        -> 204
POST   /v1/computers/:id/stop   -> ComputerInfo
POST   /v1/computers/:id/start  -> ComputerInfo
```

Husk never deletes a chat's computer on its own, and `DELETE` refuses one (422) unless
`?confirm=` repeats its id. On docker and podman a chat's or a bot's computer keeps its
files and browser logins for its next computer; `?erase=true`, with `?confirm=`, takes
those too, as the console's Delete does.

The create body is validated with a **strict** schema — an unknown key is a 422, not a
silently ignored typo. A `memoryMB` that quietly became "no memory limit" is exactly
the kind of failure that costs an hour.

Accepted keys: `name`, `provider`, `image`, `flavor`, `cpus`, `memoryMb`, `diskMb`,
`idleTimeoutSec`, `maxLifetimeSec`, `network`, `env`, `mounts`, `workdir`, `user`,
`persist`, `packages`, `setup`, `labels`.

```bash
curl -s localhost:7377/v1/computers \
  -H 'content-type: application/json' \
  -d '{"name":"scratch","flavor":"python","network":{"mode":"egress","allow":["pypi.org"]}}'
```

More than `maxComputers` live machines returns `E_QUOTA` with 429.

### Exec

```text
POST /v1/computers/:id/exec
body: { cmd, cwd?, env?, timeoutSec?, stdin?, tty?, user?, maxOutputBytes? }
  -> ExecResult
```

`cmd` is a non-empty string or a non-empty array of strings. `timeoutSec` is capped at
3600 and `maxOutputBytes` at 16 MiB. Disconnecting aborts the exec.

Streaming, same body:

```text
POST /v1/computers/:id/exec/stream
data: {"type":"stdout","data":"…"}
data: {"type":"stderr","data":"…"}
data: {"type":"exit","result":{ …ExecResult }}
event: done
```

### Files

```text
GET    /v1/computers/:id/fs?path=/work                       -> { entries: DirEntry[] }
GET    /v1/computers/:id/fs/read?path=/work/a.txt            -> raw bytes
PUT    /v1/computers/:id/fs/write?path=/work/a.txt           body: raw bytes -> 204
DELETE /v1/computers/:id/fs?path=/work/a.txt&recursive=true  -> 204
```

`fs/read` responds `application/octet-stream`. `fs/write` writes the request body exactly
as sent, whatever its content type, so a JSON body is a file of that JSON. A missing
`path` is a 422 naming the parameter.

```text
POST /v1/computers/:id/fs/upload?path=/work    body: a tar.gz -> { path, bytes, entries }
GET  /v1/computers/:id/fs/download?path=/work  -> application/gzip
```

Both were listed as not implemented for months, on the grounds that the server has no
multipart parser and the repo ships no tar. Both reasons turned out to be answering the
wrong question. The tar we need is not on npm — it is already inside the machine, along
with gzip, on every image husk supports and on a stock WSL. The archive is made and
unmade *there*; only bytes cross the boundary. That is also the more correct design,
since on docker, podman, fly and ssh the host cannot see the directory at all.

No multipart parser either: the body **is** the archive, not a form containing one.

Download stops at 256 MiB compressed. The archive is cut off inside the machine as it
passes that, so an accidental `path=/` fails with `E_QUOTA` once its archive is that big,
without filling the computer's `/tmp` or pulling a root filesystem into the server's
memory to be rejected afterwards. A path that is not there, and a file tar cannot read,
are each said as such. Entries start with the directory's own name (`src/…` for
`path=/work/src`), so upload such an archive to the parent, `/work`, to put it back.
`/work`'s own archive goes back through `/` only on Docker, Podman and Fly: on `local`
and `ssh`, `/` is that machine's own root.

`husk cp` still does directory copies through the provider's own mechanism (`docker cp`,
`scp`, a recursive filesystem copy), which stays the faster path when you are at a
terminal on the same host.

### Ports and terminal

```text
POST /v1/computers/:id/ports  body: { port: 8000 }  -> PortBinding
WS   /v1/computers/:id/terminal
```

`port` must be 1–65535. The response is `{ hostPort, url, publicUrl?, reachable? }`;
`reachable` says whether anything answered on `url` when the binding was made, and is
absent when the provider did not check.

The terminal socket is **not** a pty. Husk ships no native modules, so there is no
`node-pty`; `exec` with `tty: true` is as close as the providers get, and the socket
therefore carries one command per message rather than a persistent shell.

| Direction | Frame |
| --- | --- |
| server → client | `{"type":"ready","computerId":"…","workdir":"/work"}` on connect |
| client → server | a raw string, or `{"type":"exec","cmd":"ls -la"}` |
| client → server | `{"type":"resize","cols":120,"rows":32}` — **recorded, not applied** |
| server → client | `{"type":"stdout","data":"…"}`, `{"type":"stderr","data":"…"}` |
| server → client | `{"type":"exit","exitCode":0,"durationMs":41}` |
| server → client | `{"type":"error","error":"…"}` |

Resize is logged at debug level. Without a pty there is nothing to resize, and saying so
beats pretending.

## Husks

```text
GET    /v1/husks           -> { husks: HuskSummary[] }
POST   /v1/husks           body: { spec } | { yaml } -> 201 HuskSummary
GET    /v1/husks/:name     -> { spec: HuskSpec, yaml: string }
PUT    /v1/husks/:name     body: { spec } | { yaml } -> HuskSummary
DELETE /v1/husks/:name     -> 204
POST   /v1/husks/validate  body: { spec } | { yaml } -> { ok, issues? }
```

`HuskSummary` is `{ name, displayName, description, model, engine, version, tools,
triggers, computer: { enabled, flavor }, updatedAt, runCount }`, where `engine` is
`builtin`, `claude-code` or `codex`.

`PUT` requires `spec.name` to match the path. Renaming is a `DELETE` then a `POST`, so
that a rename is visibly two operations rather than an invisible one.

`POST /v1/husks/validate` is registered ahead of the resource routes so `/v1/husks/:name`
does not swallow it, and it answers **200** with `{ ok: false, issues }` rather than 422
— it is a validator, not an operation that can fail.

Creating, updating or deleting a husk re-syncs the trigger host, so a new `http` or
`cron` trigger takes effect without a restart.

## Running a husk

```text
POST /v1/husks/:name/run
POST /v1/husks/:name/run/stream
body: { input, history?, model?, vars?, maxSteps?, maxCostUsd?, approvalMode?, computerId? }
```

`input` is a string or a `ModelMessage[]` and is required:

```text
422 { "error": { "code": "E_SPEC_INVALID",
                 "message": "run requires a non-empty `input`",
                 "hint": "POST { \"input\": \"your prompt\" } or an array of ModelMessage" } }
```

`maxSteps` and `maxCostUsd` are clamped against the husk file —
`Math.min(body.maxSteps ?? spec, spec)`, and the same for the cost — so a caller can
lower a limit and cannot raise it. `maxTokens` and `timeoutSec` always come from the spec
and are not accepted from the body. The run's router gets the husk's `fallbackModels`.

<Note>
`computerId` pins the run to a machine that already exists -- a checkout you set up by
hand, a dataset, a logged-in browser profile -- instead of letting the husk bring up its
own. An id that does not exist is a `404`, checked before the model is called. Omit it
and nothing changes: the agent asks for a computer by its own key, as before.
</Note>

The streaming variant emits `RunEvent` objects verbatim from `@husk-ai/core`:

```text
data: {"type":"run_start","runId":"run_x","husk":"triage","model":"ollama/qwen2.5:7b"}
data: {"type":"step_start","step":1}
data: {"type":"tool_start","call":{"type":"tool_call","id":"c1","name":"shell","args":{}}}
data: {"type":"tool_delta","callId":"c1","tool":"shell","stream":"stdout","text":"…"}
data: {"type":"tool_end","call":{…},"output":"…","isError":false,"durationMs":812}
data: {"type":"text_delta","text":"Look"}
data: {"type":"usage","usage":{…},"cumulative":{…}}
data: {"type":"run_end","result":{…}}
event: done
```

The other events are `thinking_delta`, `message` (after every step), `tool_denied`,
`approval_required`, `handoff_required`, `computer_ready`, `warning` and `error`; `RunEvent`
in `@husk-ai/core` has every field.

The control plane assigns the run id, not the agent, and rewrites it on `run_start`,
`run_end`, `approval_required` and `handoff_required`, so one id is true in the stream, in
the store, and in the cancel call.

<Warning>
`tool_delta` carries raw command output. It is **not** passed through `redact()` — only
the `tool_result` the model reads is. See [Secrets](/security/secrets#redaction).
</Warning>

### Approvals

With `approvalMode: "ask"`, a dangerous tool call blocks and the stream emits:

```json
{ "type": "approval_required", "approvalId": "apr_x",
  "request": { "runId": "run_x", "huskId": "triage", "tool": "shell", "callId": "c1",
               "args": { "command": "ls" }, "prompt": "Allow shell?",
               "details": { "command": "ls" }, "dangerous": true } }
```

`callId` is the id of the call's `tool_start`, once it is let through.

```text
GET  /v1/approvals                 -> { approvals: PendingApproval[] }
POST /v1/approvals/:approvalId     body: { approve: boolean, remember?: boolean }
                                   -> { approvalId, approved, remembered }
```

An unanswered approval is denied after 120 seconds. [Approvals](/security/approvals) is
the full behaviour.

```text
GET  /v1/handoffs                    -> { handoffs: PendingHandoff[] }
GET  /v1/handoffs/:handoffId         -> PendingHandoff
GET  /v1/handoffs/:handoffId/screen  -> image/jpeg (header x-husk-viewport: <w>x<h>)
POST /v1/handoffs/:handoffId/input   body: click | scroll | text | key  -> 204
POST /v1/handoffs/:handoffId/done    -> { handoffId, outcome: "done" }
```

While a run waits on a person, its stream says so, with the handoff to answer:

```json
{ "type": "handoff_required", "handoffId": "hnd_x",
  "request": { "runId": "run_x", "huskId": "triage", "reason": "Enter the 2FA code", "computerId": "cmp_x" } }
```

A handoff resumes only when a person posts `/done`. A dropped connection or a timeout
leaves the run paused, and cancelling the run ends the wait. The screen and input
endpoints work only while the handoff is open, never launch a browser, and accept mouse
and keyboard events only: no navigation, no script, no raw CDP. Typed text is not
logged. The console's Handoffs panel uses all four.

### Runs

```text
GET    /v1/runs?husk=&limit=50&cursor=  -> { runs: RunSummary[], nextCursor? }
GET    /v1/runs/:runId                  -> { result, events }
DELETE /v1/runs/:runId                  -> 204, cancels first
POST   /v1/runs/:runId/cancel           -> 202
```

`limit` is clamped to 1–500 and defaults to 50. `cursor` is the opaque `nextCursor` from
the previous page, base-36.

`GET /v1/runs/:runId` returns the `RunResult` once the run has finished. **While a run
is still in flight it returns the `RunSummary` in the `result` slot** instead, so a
poller can see status without special-casing a 404. Tell them apart by `stopReason`,
which only a `RunResult` has.

`POST /v1/runs/:runId/cancel` is idempotent. An already-finished run answers 202 with
`{ runId, cancelled: false, status: "complete" }` rather than an error, because a client
racing a completing run should not have to distinguish the two outcomes.

## Sessions

```text
GET  /v1/sessions/discover?source=&path=  -> { sessions: DiscoveredSession[] }
POST /v1/sessions/import                  -> { transcript } | { source, choices }
POST /v1/sessions/distill                 -> { transcriptId, distilled, spec, yaml, engines, continues }
POST /v1/sessions/distill/stream          -> SSE
```

`import` takes `{ path?, content?, source?, pick? }` and needs at least one of `path` or
`content`. A file with one chat is saved and returned as `{ transcript }`. A file that
holds many, such as a ChatGPT export or Cursor's `state.vscdb`, answers
`{ source, choices }`, each choice `{ id, title, messages, updatedAt? }`, newest first,
and keeps nothing; ask again with `pick` set to a choice's `id`.

`distill` takes `{ transcriptId?, transcript?, useModel?, model?, engine? }`. `useModel`
must be exactly `true` to use a model; anything else runs the free heuristic path.
`engines` lists what the draft can run on, best first: the chat's own app's CLI when it
is installed, any other installed CLI, then `builtin`. `engine` picks one of them, and
`continues` says whether Claude Code would go on with the chat itself rather than start
from the draft.

The streaming variant takes no `engine`. It emits three progress frames then the result:

```text
data: {"type":"progress","stage":"scanning","pct":0.1}
data: {"type":"progress","stage":"extracting","pct":0.4}
data: {"type":"progress","stage":"merging","pct":0.8}
data: {"type":"done","spec":{…},"distilled":{…},"yaml":"…"}
event: done
```

<Note>
There is one mapper: `toSpec` in `@husk-ai/sessions`. This route calls it, and so does
`husk distill`, so the same transcript produces the same husk.yaml either way. It
writes `metadata.distilledConfidence` and `metadata.distillerNotes` — see
[metadata and origin](/chat-to-bot/husk-yaml#metadata-and-origin). It used to be
three mappers with two spellings of those keys, which meant a husk imported over
HTTP carried provenance that nothing looked for.
</Note>

## Models

```text
GET  /v1/models              -> { models: ModelInfo[], providers: [...] }
POST /v1/models/chat         body: ChatRequest -> ChatResponse
POST /v1/models/chat/stream  body: ChatRequest -> SSE of StreamEvent
```

`GET /v1/models` probes providers four at a time; a dead Ollama does not stall the
picker. Each `providers[]` entry is
`{ id, displayName, priority, available, reason?, hint? }`.

The chat body is validated against a strict-ish schema covering `model`, `messages`,
`system`, `tools`, `toolChoice`, `temperature`, `topP`, `maxTokens`, `stop`, `thinking`,
`responseFormat` and `metadata`. `messages` must be non-empty.

## Events

```text
WS /v1/events
```

On connect the server sends a `hello` frame listing the topics and the currently active
runs. Send `{"type":"subscribe","topics":["computers","runs"]}` to filter; the server
replies `subscribed` and then **replays the buffered history** for those topics before
streaming live traffic. `{"type":"ping"}` gets a `pong`.

Topics: `computers`, `runs`, `providers`, `triggers`, `adapters`, `reaper`.

Each frame is `{ type, at, topic, payload }`.

The `adapters` topic carries `adapter_started` and `adapter_stopped`, each with the husk
and the trigger type. See [Triggers](/chat-to-bot/triggers#discord-slack-and-telegram).

## Triggers

Registered once at boot as three wildcard routes plus a listing, with the dispatch
tables rebuilt by `sync()` whenever a husk changes.

```text
ALL  /v1/t/<husk><path>   an `http` trigger
POST /v1/w/<husk><path>   a `webhook` trigger
ALL  /v1/a/<husk>/…       a chat app's own events, such as Slack's Events API
GET  /v1/triggers         -> { triggers: MountedTrigger[], cron: […] }
```

[Triggers](/chat-to-bot/triggers) covers prompt extraction, HMAC verification and the
cron scheduler.

## The console

`GET /` serves the built dashboard, from `@husk-ai/console-assets` or, in a checkout,
`apps/console/dist`, with a single-page-app fallback for deep links, and a static
placeholder page listing the useful endpoints when there is none. A missing console
never stops the server booting.

<Note>
Earlier revisions of these docs said the control plane would not start when a built
console was present. That is no longer true — the static plugin is registered with
`wildcard: false` and the SPA fallback is installed as a not-found *fallback* rather
than as a second not-found handler, so it no longer collides with the API's own.
Verified against this checkout with `apps/console/dist/index.html` in place.
</Note>

## The SDK

`@husk-ai/sdk` is the typed client for this API, tested against a real server. It covers
health, doctor, events, computers, husks, runs, approvals, sessions and models; the
[other routes](#other-routes) have no methods. See [SDK](/reference/sdk).
